# Modeo 项目目标（v0.2）

## 1. 一句话目标

做一款个人可深度定制的 AI Agent 桌面应用：普通对话、代码开发、角色创作三种模式一键切换。每种模式是一套**可见、可编辑、可替换的 harness 配置**——用户看得懂、改得动、能掌控模型行为。

## 2. 产品愿景

现有 Agent 产品要么只做一件事，要么功能堆叠但内部不透明。Modeo 验证的假设：

> 用户需要的不是一个"什么都能干的 Agent"，而是一个"能按场景切换工作方式的 Agent，且每种方式自己都能看懂、改得动"。

模式切换在工程上 = harness 切换：提示词策略、工具集、上下文管理、UI 能力各不同，但共享同一个核心运行时。

## 3. 差异化定位

1. **纯净模式（Transparent Chat）**：第一种"零隐藏提示词"聊天体验。任何模式下都能查看当前生效的系统提示词、工具列表、上下文策略。
2. **模式即配置（Harness as Config）**：三个模式不是三套代码，而是三份 YAML harness 配置文件；用户可复制、修改、新建模式。
3. **角色卡工程化（Character as File）**：角色预设是规范化 YAML 文件，支持表单/源码双视图、schema 校验、CCv3 角色卡导入导出，天然可分享、可 diff、可进版本库。

## 4. 三模式定义

| 维度 | 普通 Chat | Code | 角色扮演/写作 |
|---|---|---|---|
| 系统提示词 | 无任何注入（最小必要除外，透明展示） | 完整代码 harness | 由角色 YAML 生成的动态人设 |
| 工具 | 默认无，可按会话开启 | shell、文件读写、编辑、测试 | 仅对话 + 角色记忆 |
| 上下文 | 简单压缩 | checkpoint、审批、仓库感知 | 角色记忆、world_state |
| UI 增强 | 纯对话 | 终端/工具输出、审批弹窗 | 角色侧边栏、角色卡编辑 |
| 默认模型 | 快速通用 | 代码强模型 | 长上下文/创作向 |

## 5. 功能范围

### MVP（v1，本项目验收范围）

- [x] 三模式完整可用：普通 Chat、Code（最小集）、角色扮演/写作
- [x] 提示词透明面板：任何模式可查看当前生效的完整系统提示词与工具列表
- [x] 普通 Chat 模式零注入：system prompt 为空（透明展示为空）
- [x] Code 模式最小集：沙箱工作区、文件读写、shell 执行、危险操作审批
- [x] 角色 YAML schema + 编辑器（表单/源码双视图）+ 校验错误提示
- [x] CCv3 角色卡导入导出（JSON；PNG tEXt 导入）
- [x] 每模式独立默认模型配置（支持 mock 与 OpenAI 兼容 API）
- [x] 会话级模式切换，切换时明确提示配置已变更
- [x] 本地优先：会话、角色、配置默认存本地
- [x] Code 模式 AGENTS.md 仓库约定识别（v0.1.1 落地）
- [x] Code 模式 undo/checkpoint：变更前自动快照、一键恢复（v0.2 落地）
- [x] 角色世界状态记忆（world_state）：会话级事实键值对，模型经工具更新、侧栏可编辑，持续注入系统提示词（v0.2 落地）
- [x] Code 模式自动跑测试（run_tests）与 diff 审查（review_changes）（v0.2.1 / v0.3 落地）
- [x] 斜杠命令体系：/goal 设置会话目标、/压缩 调用模型压缩历史、/clear 清空历史、/模式 切换模式、/new 新建会话、/help 帮助；输入框 / 弹出补全列表（v2.7 落地）

- [x] 上下文压缩：src/runtime/compress.js 以模型摘要替换历史，保留最近若干条 user/assistant 消息；notice 消息不进模型上下文

## 6. 技术目标

1. **单一核心运行时**：工具调用循环、流式输出、上下文管理、会话存储全模式共用；模式 = 配置。
2. **Harness 配置 YAML 化**：每个模式一份 YAML（systemPrompt、tools、sandbox、approval、context、defaultModel、ui）。
3. **提示词全透明**：运行时记录实际发送给模型的完整 prompt 结构，API 可查；纯净模式保证零额外注入。
4. **安全模型前置**：沙箱工作区、路径越界拒绝、危险命令审批。
5. **角色内容安全**：角色 YAML 当数据处理，不当指令执行；顶层护栏独立于角色配置。
6. **本地优先、零依赖**：v1 不依赖 npm 联网安装，node 内置模块即可运行。

## 7. 成功衡量指标

- 技术侧：code 模式沙箱越界尝试 100% 被拒绝；角色 OOC 率通过示例对话控制；新增模式仅需改配置。
- 工程侧：`node --test` 全绿；`node server.js` 一键启动；API 验收清单全部通过。
- 产品侧：三模式切换无阻塞、有明确提示；提示词透明面板可用。

## 8. 里程碑与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| M0 | 核心运行时 + 普通 chat + 透明面板 | 纯净对话可用，注入内容 100% 可见 |
| M1 | Code 模式最小集（沙箱+文件+shell+审批） | 能在本地工作区完成"改文件→跑命令→汇报" |
| M2 | 角色 YAML + 编辑器 + CCv3 导入导出 | 导入 CCv3 卡即可开始角色扮演 |
| M3 | 模式切换打磨 + 每模式模型路由 | 三模式全流程无阻塞 |

## 9. 明确不做（Non-Goals，v1）

- 不做云端托管平台（本地桌面应用；Electron 封装放 v2）
- 不做通用超级 Agent（不追求一个会话干所有事）
- 不做模型训练/微调（只做 harness 与产品层）
- 不做商业化/付费墙
- 角色模式保留基础内容边界，不做无限放纵平台

## 10. 交付审查机制

本项目采用**子 Agent 审查门禁**：主 Agent 完成开发并自测后，由独立审查子 Agent 对照本文件与 `CHECKLIST.md` 逐项核验（运行测试、启动服务、调用 API、检查边界安全）。审查结论达到"基本符合项目目标要求"（M0–M2 验收项全部通过，M3 无阻塞）后，方可交付。
